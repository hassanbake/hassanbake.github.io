ایجنت کدنویسی برنامه‌ای است که فایل‌های شما را می‌خواند، دستور اجرا می‌کند، کد را
تغییر می‌دهد و آن‌قدر در حلقه می‌ماند تا خودش تصمیم بگیرد کار تمام شده. این‌ها
یادداشت‌هایی است درباره‌ی دو چیزی که طبق تجربه‌ی من تعیین می‌کند این حلقه کمک
می‌کند یا اذیت: **ایجنت چه چیزی می‌بیند** (context) و **از کجا می‌فهمیم کار درست
است** (verification). این‌ها عادت‌های کاری من است، نه پژوهش. هر جا به نوشته یا
داده‌ی کس دیگری تکیه کرده‌ام، لینکش را گذاشته‌ام و گفته‌ام کدام بخش مال اوست.

## حلقه، در یک پاراگراف

ایجنت چند فایل می‌خواند، نقشه می‌کشد، کد را عوض می‌کند، چیزی اجرا می‌کند،
خروجی را می‌خواند و دوباره شروع می‌کند. هر چیزی که می‌خواند و خروجی هر دستور در
یک فضای مشترک جمع می‌شود، یعنی **context window**، و مدل فقط از چیزی که در این
فضا هست کار می‌کند. پس در هر کار دو سؤال داریم: *چیزهای درست داخل آن رفته؟* و
*وقتی ایستاد، چه چیزی را چک کرده بود؟*

## context بودجه است، نه سطل

تیم مهندسی Anthropic این را خوب نوشته است:
[*Effective context engineering for AI agents*](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents)
(سپتامبر ۲۰۲۵). چارچوب آن‌ها این است که سؤال دیگر فقط این نیست که پرامپت را چطور
بنویسیم، بلکه این است که در هر قدم چه اطلاعاتی، از ابزار و فایل تا تاریخچه‌ی
پیام‌ها، باید در پنجره باشد. جمله‌شان صریح است:

<div class="en-block" dir="ltr" lang="en">

> Context, therefore, must be treated as a finite resource with diminishing marginal returns.

</div>

یعنی context را باید منبعی محدود دانست که بازده نهایی‌اش کم می‌شود. آن‌ها از
*context rot* هم حرف می‌زنند: هرچه پنجره پرتر شود، توان مدل در یادآوری چیزهای
داخلش کمتر می‌شود. مستندات Claude Code
([*Best practices*](https://code.claude.com/docs/en/best-practices)) بیشتر توصیه‌هایش را
روی همین محدودیت بنا کرده: پنجره سریع پر می‌شود و با پرشدنش کیفیت پایین می‌آید.

برای من این‌ها چند عادت شده است:

1. **هر نشست، یک کار.** وقتی کار بعدی بی‌ربط است، از نو شروع کنید و هزار خط
   خروجی بی‌ربط را با خودتان نکشید.
2. **بعد از دو اصلاح ناموفق، دوباره شروع کنید.** رشته‌ای طولانی از «نه، این نه»
   یعنی context پر از رویکرد غلط. نشست تازه با پرامپت دقیق‌تر معمولاً بهتر است.
   راهنمای Claude Code هم همین را می‌گوید.
3. **اشاره کنید، توصیف نکنید.** «ببین `HomePage` چطور ساخته شده و همان الگو را
   دنبال کن» بهتر از سه پاراگراف حافظه‌ی من است. فایل، قید و نمونه‌ی الگو را اسم
   ببرید.
4. **دستورهای ثابت را کوتاه نگه دارید.** بیشتر ابزارها یک فایل پروژه را اول هر
   نشست می‌خوانند (در Claude Code اسمش `CLAUDE.md` است). خطی آن‌جا جا دارد که
   حذفش باعث اشتباه ایجنت شود. چیزی که با خواندن کد معلوم می‌شود لازم نیست.
5. **خواندن را به یک کمک‌کار بسپارید.** گشتن در کدبیس context را می‌خورد. یک
   sub-agent می‌تواند بیست فایل را در پنجره‌ی خودش بخواند و یک پاراگراف برگرداند.
   این یکی از الگوهای همان نوشته‌ی Anthropic است، کنار نوشتن یادداشت در فایلی که
   ایجنت بعداً دوباره بارش کند.

هیچ‌کدام عجیب نیست. بیشتر شبیه مرتب‌کاری است، و بیشتر نشست‌های بد من از همین‌جا
آمده‌اند.

## «تمام شده به نظر می‌رسد» سیگنال نیست

این جمله از راهنمای Claude Code شیوه‌ی کار مرا عوض کرد:

<div class="en-block" dir="ltr" lang="en">

> Claude stops when the work looks done. Without a check it can run, "looks done" is the only signal available, and you become the verification loop.

</div>

یعنی ایجنت وقتی می‌ایستد که کار تمام‌شده به نظر برسد، و اگر چکی نداشته باشد که
بتواند اجرایش کند، «به نظر تمام است» تنها سیگنال است و خودِ شما حلقه‌ی بررسی
می‌شوید. اگر تنها چک این باشد که من diff را بخوانم، هر اشتباهی منتظر توجه من
می‌ماند. پس عادت دوم این است که **پیش از شروع چیزی به ایجنت بدهید که pass یا fail
برگرداند**: مجموعه‌ی تست، exit code بیلد، linter، اسکریپتی که خروجی را با یک
نمونه مقایسه کند، یا یک اسکرین‌شات برای مقایسه.

یک مثال کوچک. این دو درخواست را مقایسه کنید:

```text
Write a function that parses durations like "1h30m".
```

```text
Write parseDuration(input) that returns seconds. "1h30m" is 5400, "45s" is 45,
"2h" is 7200, "" and "1x" throw. Put these as assertions in the same file and
run it.
```

نوشتن دومی یک دقیقه وقت می‌گیرد و دو کار می‌کند: حدس درباره‌ی معنای «parse» را
حذف می‌کند و حلقه‌ای به ایجنت می‌دهد که خودش ببندد. این یکی را با Node 22 و یک
regex ساده و `node:assert` امتحان کردم و هر پنج assertion پاس می‌شود:

```js title="duration.mjs"
import assert from "node:assert/strict";

export function parseDuration(input) {
  const m = /^(?:(\d+)h)?(?:(\d+)m)?(?:(\d+)s)?$/.exec(input.trim());
  if (!input.trim() || !m) throw new Error(`bad duration: ${input}`);
  const [, h = 0, mi = 0, s = 0] = m;
  return Number(h) * 3600 + Number(mi) * 60 + Number(s);
}

assert.equal(parseDuration("1h30m"), 5400);
assert.equal(parseDuration("45s"), 45);
assert.equal(parseDuration("2h"), 7200);
assert.throws(() => parseDuration(""));
assert.throws(() => parseDuration("1x"));
```

سه چیز هم خودم اضافه کرده‌ام:

- **شواهد بخواهید، نه حکم.** «کار می‌کند» یک ادعاست. دستوری که اجرا شده و
  خروجی‌اش شواهد است، و خواندنش از تکرار کردنش سریع‌تر است.
- **در یک context تازه بازبینی کنید.** ایجنتی که کد را نوشته به آن متمایل است.
  نشست یا sub-agent دیگری که فقط diff و نیازمندی‌ها را می‌بیند، آن را با معیار
  خودش می‌سنجد. همان راهنما هشداری هم دارد که من درست یافته‌ام: بازبینی که گفته‌اند
  «کاستی پیدا کن» حتی برای کار سالم هم چیزی پیدا می‌کند، پس بخواهید فقط چیزهایی
  را گزارش کند که به درستی یا نیازمندی‌های گفته‌شده مربوط است.
- **اگر نتوانم تأییدش کنم، منتشرش نمی‌کنم.** راهنما هم همین را می‌گوید. بعضی
  چیزها، مثل تغییر ظاهری یا مهاجرت داده، نیاز به نگاه انسان دارند. اشکالی ندارد،
  به شرط این‌که تصمیم من باشد و شکافی نباشد که ندیده‌ام.

## چرا به حس سرعتم اعتماد نمی‌کنم

METR در ۲۰۲۵
[یک مطالعه‌ی تصادفی‌شده](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)
منتشر کرد: ۱۶ توسعه‌دهنده‌ی باتجربه‌ی متن‌باز، روی ۲۴۶ issue واقعی در مخزن‌های
خودشان، و برای هر issue به‌طور تصادفی تعیین شده بود که ابزار هوش مصنوعی مجاز
باشد یا نه. با مجاز بودن AI، توسعه‌دهنده‌ها ۱۹٪ بیشتر وقت گذاشتند. پیش از شروع
انتظار ۲۴٪ تندتر شدن داشتند، و بعد از آن هم باور داشتند AI آن‌ها را ۲۰٪ سریع‌تر
کرده است.

نویسنده‌ها درباره‌ی این‌که این نتیجه چه چیزی را نشان می‌دهد و چه چیزی را نه
محتاط‌اند. این عکسی از ابزارهای اوایل ۲۰۲۵ در یک موقعیت است، با گروه کوچکی از
توسعه‌دهنده‌ها روی کدبیس‌هایی که خوب می‌شناختند، و صفحه‌شان حالا می‌گوید داده‌ی
تازه‌تری هم هست. من آن را به معنای «AI کندتان می‌کند» نمی‌خوانم. آن را هشداری
درباره‌ی خوداظهاری می‌خوانم: این‌که چیزی چقدر *سریع حس می‌شود* و چقدر *طول
می‌کشد* می‌تواند از هم جدا شود. چک ثابت و حلقه‌ی بازخورد کوتاه تا حدی راهی است
که خودم را صادق نگه دارم.

<div class="callout">

**چه چیزی بماند.** ایجنت به اندازه‌ی چیزی خوب است که می‌بیند و چیزی که می‌تواند
چک کند. پنجره را کوچک و مرتبط نگه دارید، «تمام» را چیزی تعریف کنید که اجرا
می‌شود، و نتیجه را اندازه بگیرید، نه این‌که به حس‌تان اعتماد کنید.

</div>

## فهرست پیش از شروع هر کار

1. این نشست برای *یک* چیز است. آن چیز چیست؟
2. کدام فایل‌ها و نمونه‌ها را اول بخواند؟ اسمشان را بردم؟
3. کدام دستور برای این تغییر pass یا fail برمی‌گرداند؟
4. فایل دستورهای ثابت آن‌قدر کوتاه هست که هر خطش جایش را حق کرده باشد؟
5. وقتی بگوید «تمام شد»، چه شواهدی از او می‌خواهم؟
