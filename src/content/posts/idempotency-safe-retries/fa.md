کلاینتی از سرور می‌خواهد ۲۰ دلار از یک کارت برداشت کند. سی ثانیه بعد اتصال timeout
می‌شود. برداشت انجام شد یا نه؟ این یادداشت‌ها درباره‌ی همین یک سؤال است، و درباره‌ی
عادتی که جوابش را می‌دهد: عملیات را طوری بسازید که تکرارش بی‌خطر باشد، بعد
دوباره امتحان کنید. ایده‌ها از منابع آخر نوشته آمده‌اند، بیشتر از Brandur Leach
درباره‌ی کلیدهای idempotency در Stripe و Marc Brooker درباره‌ی retry در Amazon.
مثال کوچک و اشتباهاتش از من است.

## timeout‌ای که کسی نمی‌تواند تفسیرش کند

وقتی تماس timeout می‌شود، دقیقاً یکی از سه اتفاق افتاده است:

| چه شد | برداشت انجام شد؟ | کلاینت چه دید |
|---|---|---|
| درخواست هیچ‌وقت نرسید | نه | timeout |
| سرور پردازشش کرد، اما پاسخ گم شد | بله | timeout |
| سرور هنوز مشغول کار است | هنوز نه | timeout |

از دید کلاینت این سه یکسان‌اند. همان دیواری است که در یادداشتم درباره‌ی
[ساعت‌های لمپورت](/fa/notes/lamport-time/) بود: بدون اطلاعات اضافه نمی‌شود
پردازه‌ی خراب را از پردازه‌ی کند تشخیص داد. timeout حدسی درباره‌ی زمان است، نه
واقعیتی درباره‌ی این‌که چه شده.

## تکرار تنها راه است، و خطرناک است

کلاینت دو انتخاب دارد. رها کند، و ریسک کند که پرداخت کاربر بی‌صدا هرگز انجام
نشده باشد. یا دوباره بفرستد، و ریسک کند که اگر ردیف دوم جدول واقعیت بوده، دو بار
برداشت شود. بیشتر سیستم‌ها تکرار را انتخاب می‌کنند چون بیشتر خطاها گذرا هستند.
مقاله‌ی Marc Brooker درباره‌ی retry شرطش را ساده گفته است:

<div class="en-block" dir="ltr" lang="en">

> In general, our view is that APIs with side effects aren't safe to retry unless they provide idempotency.

</div>

یعنی APIهایی که اثر جانبی دارند، مگر idempotency داشته باشند، تکرارشان امن نیست.
عملیات **idempotent** است اگر دوبار انجام دادنش همان اثر یک‌بار را داشته باشد.
بعضی‌ها ذاتاً هستند:

| درخواست | idempotent؟ |
|---|---|
| «موجودی را بگذار ۸۰» | بله. دوبار هم ۸۰ می‌ماند. |
| «سفارش ۱۷ را حذف کن» | بله. بار دوم چیزی برای انجام نمی‌ماند. |
| «۲۰ تا از موجودی کم کن» | نه. دوبار یعنی ۶۰. |
| «یک برداشت جدید بساز» | نه. دوبار یعنی دو برداشت. |

بیشتر عملیات مفید در نیمه‌ی پایین‌اند. همیشه نمی‌شود آن‌ها را به شکل «بگذار روی»
بازنویسی کرد، پس به آن‌ها هویت می‌دهیم.

## کلیدهای idempotency

کلاینت برای *نیت* یک شناسه‌ی یکتا می‌سازد (UUID تصادفی رایج است) و همراه
درخواست می‌فرستد. تکرار همان نیت از همان شناسه استفاده می‌کند. سرور یادش می‌ماند
برای آن شناسه چه کرده، و بار دوم که شناسه را می‌بیند به‌جای انجام دوباره‌ی کار،
پاسخ اول را برمی‌گرداند. بلاگ مهندسی Stripe در
[*Designing robust and predictable APIs with idempotency*](https://stripe.com/blog/idempotency)
این را برای پرداخت‌ها شرح می‌دهد، جایی که «دقیقاً یک بار» از همه مهم‌تر است.

کوچک‌ترین نسخه‌ای که توانستم بنویسم این است. یک طرح درون‌حافظه‌ای است، نه کد
production، و برای این‌که سه نتیجه‌ی زیر را بررسی کنم محلی اجرایش کردم.

```js title="charge.mjs"
import { createHash } from "node:crypto";

const store = new Map(); // key -> { fingerprint, state, response }
let balance = 100;       // the side effect we must not repeat

const fingerprint = (req) =>
  createHash("sha256").update(JSON.stringify(req)).digest("hex");

export function charge(key, req) {
  const fp = fingerprint(req);
  const saved = store.get(key);

  if (saved) {
    if (saved.fingerprint !== fp) return { status: 422, body: "key reused with a different request" };
    if (saved.state === "running") return { status: 409, body: "still processing, retry later" };
    return saved.response;                      // replay the first answer
  }

  store.set(key, { fingerprint: fp, state: "running" });
  balance -= req.amount;                        // the effect
  const response = { status: 200, body: { balance } };
  store.set(key, { fingerprint: fp, state: "done", response });
  return response;
}
```

آن را با `charge("k1", {amount: 20})` صدا بزنید، بعد دوباره با همان آرگومان‌ها، بعد
با `charge("k1", {amount: 30})`:

1. بار اول کار انجام می‌شود. موجودی از ۱۰۰ به ۸۰ می‌رسد.
2. تکرار *همان* پاسخ را می‌گیرد. موجودی ۸۰ می‌ماند.
3. کلید تکراری با مبلغ دیگر با کد ۴۲۲ رد می‌شود و بی‌صدا تکرار حساب نمی‌شود.

سه شاخه مهم‌اند. **Replay** اصل کار است. **«running»** ردیف سوم جدول را پوشش
می‌دهد، یعنی کلاینت وقتی دوباره می‌فرستد که تلاش اول هنوز در جریان است.
**fingerprint** اشتباهی در سمت کلاینت را می‌گیرد: استفاده‌ی دوباره از یک شناسه
برای درخواستی دیگر.

### آنچه این طرح پنهان می‌کند

- **کلید و اثر باید با هم commit شوند.** اگر سرور کلید را ذخیره کند اما پیش از
  برداشت بیفتد، تکرارها موفقیتی را replay می‌کنند که هرگز رخ نداده. اگر برداشت
  کند اما پیش از ذخیره‌ی کلید بیفتد، تکرار دوباره برداشت می‌کند. با یک پایگاه
  داده، هر دو را در یک تراکنش بگذارید و کلید را unique کنید تا دو تلاش هم‌زمان
  نتوانند هر دو از چک رد شوند.
- **هر اثری در پایگاه داده‌ی شما نیست.** اگر قدمی سرویس دیگری را صدا می‌زند،
  نمی‌توان آن را در تراکنش خودتان گذاشت. تا جایی که من نوشته‌ی Stripe را می‌فهمم،
  راهش این است که درخواست را به چند قدم بشکنید، ثبت کنید کدام قدم کامل شد، و در
  تکرار از همان‌جا ادامه دهید. جزئیات را از مقاله‌ی خودشان بخوانید، نه از خلاصه‌ی من.
- **کلیدها منقضی می‌شوند.** نگه‌داشتن همیشگی‌شان گران است. آن‌ها را دست‌کم تا
  وقتی نگه دارید که کلاینت هنوز ممکن است در حال تکرار باشد. این بازه انتخابی است
  که می‌نویسمش، چون تعیین می‌کند «امن» کی دیگر درست نیست.

## نیمه‌ی دیگر: مؤدبانه تکرار کنید

idempotency یک تکرار را امن می‌کند. هیچ کاری درباره‌ی هزار کلاینت که هم‌زمان به
سروری که از قبل در تنگناست دوباره می‌فرستند نمی‌کند. Brooker این را با یک عبارت
می‌گوید: retryها «خودخواهانه»اند (selfish). کلاینتی که تکرار می‌کند از ظرفیت سرور
خرج می‌کند تا شانس خودش را بالا ببرد.

دو مشکل از همین‌جا می‌آید، هر دو از نوشته‌ی او:

- **retryها در لایه‌ها ضرب می‌شوند.** اگر پنج لایه‌ی سرویس هر کدام سه بار تکرار
  کنند، پایگاه دادهٔ خراب در انتها می‌تواند ۳⁵ = ۲۴۳ برابر بار عادی ببیند.
  پیشنهادش این است که در یک نقطه از پشته تکرار کنید و از بودجه‌ی محلی retry
  (token bucket) استفاده کنید تا وقتی خیلی چیز خراب است کلاینت دست بکشد.
- **retryها هم‌زمان می‌شوند.** کلاینت‌هایی که با هم شکست خورده‌اند با هم عقب
  می‌روند و با هم برمی‌گردند. افزودن **jitter** تصادفی به انتظار آن‌ها را پخش
  می‌کند. در شبیه‌سازی قدیمی‌تر Brooker در AWS Architecture Blog، با ۱۰۰ کلاینت
  رقیب، jitter تعداد تماس‌ها را بیش از نصف کاهش داد.

شکل رایج، exponential backoff با سقف و jitter کامل است:

```text
wait = random(0, min(cap, base * 2^attempt))
```

نکته‌ی ریز: در سرویس واقعی، سرور هم با برگرداندن راهنمای `Retry-After` یا با رد
زودهنگام وقتی بار زیاد است کمک می‌کند تا کلاینت‌ها آن را نکوبند.

**چه چیزی بماند.** timeout پرسشی است که کلاینت تنها نمی‌تواند جوابش را بدهد.
عملیات را idempotent کنید تا دوباره پرسیدن امن باشد، و پرسیدن را مؤدبانه کنید تا
سرور خراب فرصت بهبود داشته باشد.

</div>

## آنچه دوست دارم با خودتان ببرید

1. **timeout سه علت ممکن دارد** و کلاینت نمی‌تواند تشخیص دهد کدام.
2. **تکرار امن به idempotency نیاز دارد،** با طراحی («بگذار روی») یا با کلید.
3. **کلید idempotency به نتیجه‌ی ذخیره‌شده،** fingerprint درخواست، حالت «در
   جریان» و بازه‌ی انقضا نیاز دارد.
4. **کلید و اثر را با هم بنویسید،** وگرنه افتادن میان آن‌ها تضمین را می‌شکند.
5. **در یک لایه تکرار کنید، با backoff، jitter و بودجه.**

حالا وقتی به یک API نگاه می‌کنم دو چیز می‌پرسم. کدام عملیاتش idempotent نیست؟ و
وقتی یکی از آن‌ها timeout شود کلاینت چه می‌کند؟
